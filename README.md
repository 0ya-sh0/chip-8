# CHIP-8 — Emulator, Assembler & Disassembler

A CHIP-8 virtual machine written in Go, with a two-way assembler/disassembler and two independent frontends: a terminal renderer (ANSI, no GUI dependencies) and an Ebitengine-powered GUI with synthesized audio. The VM core is verified against [Timendus's CHIP-8 test-ROM suite](https://github.com/Timendus/chip8-test-suite) and every ROM in the repo round-trips byte-for-byte through the assembler/disassembler pair.

```
casm -m disasm -i game.ch8   ─┐
                                ├─►  game.asm  (readable, re-assemblable)
casm -m asm    -i game.asm  ─┘

ch8-cli game.ch8   → runs in the terminal (ANSI blocks, raw-mode keyboard)
ch8-gui game.ch8   → runs in a window (Ebitengine, 15x scaled, PCM square-wave beep)
```

---

## Architecture: Hexagonal (Ports & Adapters)

The VM core is fully decoupled from I/O. It talks to the outside world through three small interfaces (`internal/vm/provider.go`), and two adapter packages implement them independently:

```
                +-----------------------------------+
                |            CHIP-8 VM              |
                |             (Core)                |
                |                                   |
                |  - 4KB Memory      - Stack        |
                |  - Registers (V0-VF) - Timers     |
                |  - Opcode Decoder  - RNG          |
                +-----------------------------------+
                   /              |              \
    [Outbound Port]        [Outbound Port]       [Outbound Port]
           |                      |                     |
           v                      v                     v
   DisplayProvider        KeyboardProvider        SoundProvider
       /       \              /       \              /       \
      /         \            /         \            /         \
(Terminal)      (Ebit) (Terminal)      (Ebit) (Terminal)      (Ebit)
```

* **Core (`internal/vm`)** — opcode decode/dispatch, 4KB memory, 16 registers, stack, delay/sound timers, RNG, the built-in font set. Runs two independent tickers: a 500Hz instruction loop and a 60Hz timer loop, exactly matching the CHIP-8 spec's timer rate.
* **Terminal adapter (`internal/terminal`)** — renders the 64×32 framebuffer as ANSI block characters (two `█` per pixel, to keep a square aspect ratio in a monospace grid), reads raw keypresses via `stty cbreak -echo`, and beeps with the ASCII BEL character.
* **Ebitengine adapter (`internal/ebit`)** — renders into a 960×480 window (15x pixel scale), reads native key state, and plays a synthesized 440Hz square wave (16-bit stereo PCM, generated by hand — no audio file assets).

Because both adapters implement the same three interfaces, the VM itself has zero knowledge of which frontend is driving it — swapping `ch8-cli` for `ch8-gui` is a one-line change in `main.go`.

## Assembler & Disassembler (`internal/asm`, `cmd/casm`)

A from-scratch, bidirectional translator between raw `.ch8` ROMs and readable `.asm` source, covering the full 35-opcode CHIP-8 instruction set.

```bash
# Disassemble a ROM into readable assembly
go run cmd/casm/main.go -m disasm -i test-roms/2-ibm-logo.ch8 -o out.asm

# Assemble it back into a binary
go run cmd/casm/main.go -m asm -i out.asm -o out.ch8
```

**Assembler** — a two-pass design: pass one strips comments, resolves label addresses (including forward references) by walking the instruction stream and tracking address width per line; pass two encodes each instruction to 1–2 bytes. Supports hex/decimal literals, `V0`–`VF` plus the special symbols `I`, `DT`, `ST`, `K`, `F`, `B`, `[I]`, case-insensitive mnemonics, `;`/`//` comments, and labels (`loop: JP loop`). A `DATA` pseudo-op lets raw bytes — like the sprite data disassembly produces — be re-embedded losslessly.

**Disassembler** — a linear decoder: it walks the ROM two bytes at a time from `0x0200` and formats every instruction as `0xADDR:  HEXBYTES  MNEMONIC operands`, using the exact same opcode decoder the VM itself runs (`vm.ParseOpcode`). Bytes that don't decode to a valid instruction are emitted as `DATA 0xNNNN` so nothing is lost. Worth noting honestly: this is a linear disassembler with no code/data-flow analysis, so sprite bitmaps embedded after a program's final jump can occasionally decode as spurious-looking instructions where their bytes happen to match a valid opcode. That's cosmetic, not a correctness bug — see the round-trip guarantee below.

```
0x200:  00E0  CLS
0x202:  600A  LD  V0, 0x0A
0x204:  610F  LD  V1, 0x0F
0x206:  F229  LD  F, V2
0x208:  D015  DRW V0, V1, 5
0x20A:  1200  JP  0x0200
```

**Round-trip guarantee** — `disassemble → reassemble` reproduces the original binary byte-for-byte. This is enforced by an end-to-end test (`internal/asm/e2e_test.go`) that runs the full pipeline against every `.ch8` file in `test-roms/` and `test-games/` (13 ROMs total) and diffs the result against the original, reporting the exact byte offset of any mismatch.

Full instruction-set reference, syntax rules, and a worked example live in [`internal/asm/README.md`](internal/asm/README.md).

## CHIP-8 quirks — what this interpreter chose

CHIP-8 opcodes have several historically ambiguous behaviors that differ between the original COSMAC VIP and later interpreters. This implementation hardcodes the modern/common interpretation for each (no runtime toggle):

| Quirk | Behavior implemented | Opcodes |
| --- | --- | --- |
| Shift | `SHR`/`SHL` shift `Vx` in place; `Vy` is ignored | `8XY6`, `8XYE` |
| Load/store | `I` is left unmodified after register dump/load | `FX55`, `FX65` |
| Clipping | Sprites clip at the screen edge instead of wrapping | `DXYN` |
| Logic ops | `OR`/`AND`/`XOR` do not reset `VF` to 0 afterward | `8XY1`–`8XY3` |
| Jump | `BNNN` jumps to `NNN + V0` (original semantics, not the SUPER-CHIP `BXNN` variant) | `BNNN` |
| `0NNN` | Treated as a no-op, as in every modern interpreter | `0NNN` |

`test-roms/5-quirks.ch8` (from the Timendus suite) exercises exactly these cases and is confirmed against this table by running it in `ch8-cli`/`ch8-gui`. Only the base CHIP-8 opcode set is implemented — the SUPER-CHIP scrolling test (`8-scrolling.ch8`) is included in the ROM corpus for completeness but isn't supported by this VM.

## Project structure

```
cmd/
├── cli    # terminal frontend entry point  → ch8-cli
├── ebit   # Ebitengine GUI frontend entry point → ch8-gui
└── casm   # assembler / disassembler CLI  → casm
internal/
├── vm         # core interpreter: opcode decode/exec, memory, timers, provider interfaces
├── asm        # assembler + disassembler (own README with full opcode table)
├── terminal   # ANSI display, raw-mode keyboard, terminal-bell sound adapters
└── ebit       # Ebitengine display, keyboard, and synthesized-audio adapters
test-games/    # public-domain games & demo ROMs
test-roms/     # Timendus CHIP-8 test suite
```

## Controls (QWERTY mapping)

The original COSMAC VIP 16-key hex keypad, mapped to a 4×4 QWERTY grid (identical mapping in both frontends):

| CHIP-8 Hex Keypad | QWERTY Key Mapping |
| :---: | :---: |
| `1` `2` `3` `C` | `1` `2` `3` `4` |
| `4` `5` `6` `D` | `Q` `W` `E` `R` |
| `7` `8` `9` `E` | `A` `S` `D` `F` |
| `A` `0` `B` `F` | `Z` `X` `C` `V` |

## Getting started

**Requires:** Go 1.24+ (developed against 1.26).

**Linux Ebitengine (GUI) dependencies** — the GUI build needs X11 and audio headers:

```bash
sudo apt install -y libx11-dev libxrandr-dev libxcursor-dev \
    libxinerama-dev libxi-dev libxxf86vm-dev libgl1-mesa-dev libasound2-dev
```

### Run a ROM

```bash
# GUI (recommended)
go run cmd/ebit/main.go test-games/cavern.ch8

# Terminal
go run cmd/cli/main.go test-games/cavern.ch8
```

### Build all three binaries

```bash
./build.sh
```

Produces `dist/ch8-gui`, `dist/ch8-cli`, and `dist/casm`.

## Testing

```bash
go test ./...
```

- `internal/asm` — round-trip fidelity tests for the assembler/disassembler pair, including the full-corpus end-to-end test described above.
- `internal/vm` — opcode decoding.

Opcode *semantics* (register/memory/display state after execution) are additionally exercised interactively via the Timendus test-ROM suite in `test-roms/`, run through either frontend.
